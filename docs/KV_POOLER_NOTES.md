# 新しいプーラー（Qwen3-1.7B 土台）の探索メモ

目的：4GB 級の端末（第3世代 SE、普及帯 Android）でアプリが使えるメモリ（アプリ全体で 1.3〜1.5 GB 目安）に収まる最大のモデル
（Qwen3-1.7B 4bit、約 0.95 GB）を、ハイパーネットで KV キャッシュ一定のまま長い思考に使う。第一原理はプーラー ≦ KV。
プーラーの最適化目標はフル版（KV 全保持）の出力トークン分布の再現（GPTQ が層の出力を合わせるのと同じ考え方）。

## 土台の実力（ユースケース 197 問、検索なし、DeepSeek 判定、4o-mini と比較）
| | 解決率 | 4o-mini より好まれた |
|---|---|---|
| deep-charger 2.1.0 | 8% | 6.6% |
| Qwen3-1.7B（思考あり） | 46% | 9.4% |
| 4o-mini | 86% | — |

## KV を単純に捨てた場合（MATH-500 Lv4-5 64 問、8000 トークン）
| | 正答 | 完走 |
|---|---|---|
| 全 KV（vLLM） | 60.9% | 43/64 |
| 直近 768 のみ（HF） | 51.6% | 38/64 |
| 直近 2048 のみ（HF） | 75.0% | 52/64 |
全 KV だけエンジンが違う（vLLM）。2048 が全 KV を上回るのは要確認（同一エンジンでの全 KV 測定が未実施）。

## 方式の比較（教師強制、フル版との KL・最有力トークン一致率、保留トレース MATH 64 本 / 混合 60 本）
露出窓 W、スロット m、C トークンごとに窓から出た分をスロットへ畳み込む（繰り返し）。

| 方式 | W | m | KV トークン | MATH KL / 一致 | 混合 KL / 一致 |
|---|---|---|---|---|---|
| 捨てる | 512 | 0 | 512 | 0.198 / 89.6% | 0.174 / 90.2% |
| 学習コードブック | 512 | 64 | 576 | 0.189 / 89.8% | 0.164 / 90.6% |
| **当てはめ畳み込み R256** | 512 | 64 | 576 | **0.098 / 94.1%** | **0.074 / 94.7%** |
| 捨てる | 256 | 0 | 256 | 0.280 / 87.4% | 0.270 / 87.3% |
| 当てはめ R64 | 256 | 64 | 320 | 0.174 / 92.0% | 0.137 / 92.8% |
| 当てはめ R256 | 256 | 64 | 320 | 0.150 / 92.3% | 0.122 / 93.0% |
| **当てはめ R256** | 256 | 128 | 384 | **0.094 / 94.0%** | **0.077 / 94.6%** |
| 捨てる | 128 | 0 | 128 | 0.404 / 84.4% | 0.402 / 83.6% |

- **学習コードブック**（`tools/kvpool.py --fold learned`）：各層・各 KV ヘッドに学習した符号帳で、出ていくトークンをスロットへ柔らかく割り当てて平均する。
  KL を目的に 500 本で学習。改善は 5% だけ。
- **当てはめ畳み込み**（`--fold fit`、重みなし）：過去のクエリの見本（R 個/ヘッド、一様リザーバ）と窓のクエリが、
  [旧スロット + 出ていく塊] から読む注意出力を変えないように、注意が集まるキーを m 個選び、質量（加算マスク）を非負最小二乗、
  値を最小二乗で解き直す。KL を半分以下にした。
- スロットは窓より効率が良い：W256+m128（384 トークン分）が W512+m64（576 トークン分）と同等。
- 1 回だけ追い出す試験（`tools/kvfit_study.py`）では、未来のクエリで当てはめると 64 スロットでほぼ完全に再現できた
  （W1024 で一致 97.5%）。足りないのは容量ではなく「未来のクエリの予測」で、過去クエリの見本がそれをかなり埋める。

## メモリ（Qwen3-1.7B、KV 112 KB/トークン fp16）
- W256 + m128：KV 42 MB。リザーバ R256 × 16 ヘッド × 128 × 2B × 28 層 = 29 MB。プーラー ≦ KV を満たす。
- 畳み込みは C=128 トークンごとに 1 回。計算は層×KV ヘッドごとの小さな最小二乗（m×m）と非負最小二乗（反復 100 回）。

## 次
- 生成ループに入れた MATH 正答率（当てはめ W256 m128 vs 捨てる W256、32 問）→ 箱 VS。
- W をさらに縮めてスロットを増やす（W128 m256 など）、R の大きさ、畳み込みの頻度 C。
- 同一エンジンでの全 KV 正答率（2048 窓が全 KV を上回った件）。
- 端末実装：MLX（キャッシュ配列の書き換え + 加算マスク）、llama.cpp（KV の直接書き込み）。

## SP 追い出し方式（deep-charger 踏襲、tools/sp_qwen3.py）の窓ゼロ検証（2026-10-23）
窓ゼロ = [プロンプト | SP 32 個] だけで次の 1 トークン（`--spnext`）。KL はその本の初見データ上（学習ログ）と保留 MATH 16 本（profile）。

- **位置の印の大きさの不具合**：プーラーの正弦波位置は大きさ sqrt(H/2) = 32、Qwen3 の埋め込みは約 1.5。
  キー・値の 9 割以上が位置で、SP は中身をほぼ運べていなかった（窓ゼロ KL 5.2〜5.8、上位一致 6%）。
  元の deep-charger も同じ式だが、元のモデルは埋め込みが大きく影響が小さかった。
  `--pe-norm`（位置を埋め込みの平均ノルムにそろえる）と `--pe-rev`（最新トークンを 0 番）で修正。
  これ以前の数字の掃引（S・maxD・層数）は窓が全部を補っていた条件なので、窓ゼロでは当てはまらない。
- **コピーの上限**（`tools/sp_oracle.py`、SP = 直近 S トークンの埋め込みそのもの）：S=1 12.6、S=8 2.55、**S=32 0.79**。
  SP 32 個で KL 1 付近は原理的に届く。

| 段階 | 内容 | 窓ゼロ KL（学習ログ） |
|---|---|---|
| C | 旧位置、全層 FFT | 6.06 → 5.7（625 本）横ばい |
| D | 修正後、新プーラー 1 層、本体固定 | 6.8 → 4.39（800）→ ~3.9（1800） |
| E | D から全層 FFT + プーラー | ~3.97 → ~3.46（450〜650 で横ばい） |
| F | 修正後、新プーラー 3 層、本体固定 | 4.47（550）→ 4.01（800）。D より 150〜200 本ぶん速い |

E（600 本）の保留評価：窓ゼロ 3.02（段階 B 途中 5.2〜5.6）、窓 1-7 2.01、8-63 0.86、64-511 0.34、512+ 0.23。
運用ループ MATH 0.212 / 混合 0.196（段階 A 0.079 / 0.066）。窓ゼロだけで本体を動かすと長い窓が崩れる。

重み（HF archive/sp3）：spD_spnext_penorm_t1800.pt、spE_spnext_penorm_fft_t600.pt、spF_L3_spnext.pt、各ログ。
